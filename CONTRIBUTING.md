# Как участвовать в проекте

Проект — гайд для выездных мастеров ИТ-ремонта: страница для телефона, её текстовая версия и записка техдиру. Всё собирается из JSON-текстов и профиля компании. Мы рады исправлениям опечаток и ошибок, новым шагам и этапам, улучшениям сборки и страницы, документации.

Участвуя в проекте, вы принимаете [правила поведения](CODE_OF_CONDUCT.md). Об уязвимости пишите не в открытый issue, а по правилам из [SECURITY.md](SECURITY.md).

Подробнее о проекте: [архитектура](docs/architecture.md), [прайс](docs/pricelist.md), [приватность](docs/privacy.md), [как раздать мастерам](docs/deploy.md). Почему проект устроен именно так, объясняют [записи решений](docs/adr/README.md); значения слов проекта — в [словаре](CONTEXT.md).

## Что нужно

- Python 3.10 или новее. Других зависимостей нет: проект использует только стандартную библиотеку, `pip install` не нужен. В примерах команда называется `python`; если у вас Python запускается как `python3`, замените.
- Git.
- Необязательно: Node.js (`node`). Через него тесты проверяют логику страницы: расчёт отчёта, готовность, акт. Без `node` эти тесты пропускаются с пометкой. В CI node установлен и задана переменная `REQUIRE_NODE=1`: без node тесты там падают, чтобы страница не осталась непроверенной. Её можно задать и у себя.

## Как поставить и запустить

Bash (Linux, macOS, Git Bash):

```bash
git clone https://github.com/Alpha-Oi/field-tech-guide.git
cd field-tech-guide
python guide/build.py
```

PowerShell (Windows):

```powershell
git clone https://github.com/Alpha-Oi/field-tech-guide.git
cd field-tech-guide
python guide/build.py
```

Сборка кладёт демо в папку `dist/`: `index.html` (страница), `guide.md` (текст для чата и печати), `for-techdir.md` (записка техдиру). Откройте `dist/index.html` в браузере. Папка `dist/` в git не попадает.

Свой гайд с данными компании собирается из своего профиля и прайса, их кладут в `private/`: см. [docs/deploy.md](docs/deploy.md).

## Проверка перед коммитом

Одна команда проверяет всё: тесты, контент с профилем и прайсом, утечки, актуальность графика.

```bash
python -m unittest discover -s guide/tests -t . && python guide/build.py --check && python tools/check_public.py && python tools/make_charts.py --check
```

В PowerShell 5.1 оператор `&&` не работает, поэтому команды идут по одной (в PowerShell 7 можно и через `&&`):

```powershell
python -m unittest discover -s guide/tests -t .
python guide/build.py --check
python tools/check_public.py
python tools/make_charts.py --check
```

- Тесты — стандартный `unittest`. Один файл: `python -m unittest guide.tests.test_build`.
- `python guide/build.py --check` проверяет контент, профиль и прайс строго: любая неизвестная переменная профиля — ошибка. Ошибки печатаются по-русски с указанием места.
- `python tools/check_public.py` ищет в файлах репозитория то, что принадлежит компании (подробнее — в разделе про приватность ниже).
- `python tools/make_charts.py --check` сверяет график `docs/img/steps-by-stage.svg` с тем, что получается из `guide/content/*.json`. Если вы добавили, убрали или перенесли шаг, график устарел: перестройте его командой `python tools/make_charts.py` и закоммитьте обновлённый файл вместе с правкой контента, а `python tools/make_charts.py --check` подтвердит, что файл актуален. Править SVG руками не нужно: проверка заметит расхождение.

Если у вас есть список слов `private/markers.txt`, проверка ищет и их.

Новый тест сначала запустите и убедитесь, что он падает по той причине, которую проверяет, и только потом пишите код.

## Как добавить этап или шаг

Тексты правятся без касания вёрстки и кода: страница, `guide.md` и записка собираются из одних и тех же JSON.

Файлы в `guide/content` читаются по порядку имён: `10-start.json`, `20-kit.json` и так далее; номер в начале имени задаёт порядок этапов. Файл этапа состоит из блока `stage` и списка шагов `steps`. Памятка на заявку лежит в одном файле с ключом `cheatsheet` (`90-cheatsheet.json`); новая форма отчёта — это новый объект в её списке `reports`, правка кода не нужна.

Блок `stage`:

| Поле | Что это |
|---|---|
| `id` | идентификатор этапа: `s1`, `s4b` |
| `title` | название; начинается с «Этап N. », где N совпадает с номером в `id` (для `s4b` в тексте — «4а») |
| `intro` | одна-две строки о том, что делаем на этом этапе |
| `steps` | список шагов (лежит рядом с блоком `stage`, на верхнем уровне файла) |

Шаг:

| Поле | Обязательно | Правило |
|---|---|---|
| `id` | да | уникален во всём гайде; вид `s<номер этапа>[буква]-<две цифры>`: `s1-01`, `s4b-03`. **Не меняется после выпуска**: по `id` страница хранит прогресс на телефонах |
| `title` | да | коротко: повелительное наклонение или название предмета |
| `kind` | да | `do` — действие (кнопка «Сделано»), `buy` — купить («Куплено»), `know` — знать («Прочитал») |
| `optional` | нет | `true` — блок «Дополнительно»; шаг не входит в «Готов к первой заявке» |
| `lead` | да | одно-два предложения: что сделать и зачем |
| `points` | нет | список пунктов; для `do` — подшаги по порядку |
| `send` | нет | готовые сообщения для чата: объекты с `label` и `text`; в `text` можно писать `{{order}}` и `{{phone}}` — их подставит страница из полей «Памятки на заявку» |
| `links` | нет | объекты с `label` и `url`; после подстановки профиля `url` обязан начинаться с `https://` |
| `tip` | нет | одна врезка «Совет» |
| `proof` | для `do` и `buy` | начинается со слов «Готово,»: что должно появиться, когда шаг сделан (сообщение диспетчера, скрин, учётка) |
| `reqs` | да | непустой список идентификаторов требований вида `R05` или `G18` (буква и число, иногда с буквой в конце: `R75i`). Возьмите идентификаторы соседних шагов по теме; полный список владелец проекта ведёт у себя, спросите в issue, если не уверены |

Строки — обычный текст. Единственная разметка — `**жирный**`. Данные никогда не вставляются в страницу как HTML.

Образец этапа с одним шагом (в `guide/content` его нет, это только пример формата):

```json
{
  "stage": {
    "id": "s9",
    "title": "Этап 9. Пример этапа",
    "intro": "Одна-две строки о том, что делаем на этом этапе."
  },
  "steps": [
    {
      "id": "s9-01",
      "title": "Проверь связь с диспетчером",
      "kind": "do",
      "lead": "Напиши диспетчеру в чат мастера и дождись ответа.",
      "points": [
        "Открой чат мастера в {{app_name}}",
        "Отметь диспетчера через @ и отправь сообщение"
      ],
      "send": [
        { "label": "Проверка связи", "text": "{{dispatcher_handle}} Привет, на связи" }
      ],
      "proof": "Готово, когда в чате есть твоё сообщение и ответ диспетчера.",
      "reqs": ["R05"]
    }
  ]
}
```

Всё, что принадлежит компании (название приложения, ник, ссылка, цена, процент), пишите переменной профиля: `{{app_name}}`, `{{dispatcher_handle}}`, `{{price_cleaning}}`. Новую переменную:

1. впишите в текст как `{{имя}}` (латинские буквы, цифры и `_`; имена `order` и `phone` заняты);
2. опишите в [guide/profiles/VARS.md](guide/profiles/VARS.md): имя, смысл, пример;
3. добавьте нейтральное значение в `guide/profiles/demo.json` (круглые вымышленные примеры, ссылки вида `https://example.com/...`).

Список переменных, которые нашлись в контенте, печатает `python guide/build.py --list-vars`. После правки запустите проверку целиком. С флагом `--manifest PATH` сборка дополнительно проверяет покрытие списка требований шагами; список ведёт владелец проекта.

## Как добавить позиции прайса

Прайс — отдельный JSON, он не часть текстов. Демо-прайс с вымышленными услугами — `guide/profiles/demo-pricelist.json`. Чтобы добавить позицию, допишите объект в `items` (уникальный `id`, номер `no` строкой, `group`, `name`, `kind`, `price`, `description`) или строку в таблицу «модель × услуга» из `matrices`. Полная схема, виды цен и правила проверки — в [docs/pricelist.md](docs/pricelist.md).

Проверить прайс: `python guide/build.py --check --pricelist путь/к/прайсу.json`. Настоящий прайс компании лежит в `private/pricelist.json` и в git не попадает.

## Правила честных текстов

Гайд учит мастера работать честно. Эти правила важнее красивой формулировки; предложения, которые им противоречат, не принимаются.

- Обращение на «ты», дружелюбно и коротко. Шаги — в повелительном наклонении. Без мата и грубых оценок клиентов и коллег.
- Без давления на клиента: ни пугать, ни торопить. Цель мастера — чтобы клиент понял, что происходит, и принял осознанное решение.
- Без завышения цен и дробления услуг: цена по прайсу, не выше; сумма не разбивается на строки ради вида.
- Без имитации работы: то, что мастер показывает клиенту, он делает на самом деле.
- Без нелицензионного ПО: никаких активаторов и «взломанных» сборок. Лицензии — вопрос клиента, мастер напоминает о них.
- Цены, проценты и ставки — только как ориентиры (переменные профиля), без обещаний дохода.
- Названия кнопок и статусов — в «ёлочках» и точно, как в приложении. Нет данных (ссылки, ника, цены, формы) — ставьте видимую заглушку в квадратных скобках, например `[ссылку выдаёт техдир]`, и ничего не выдумывайте.

## Приватность

Репозиторий публичный, поэтому в нём нет ничего, что принадлежит компании.

- В публичных файлах не должно быть названий приложений компании, ников, имён людей, ссылок на магазины, цен и процентов, номеров заявок. Всё это — переменные профиля; в демо — нейтральные примеры (`example.com`, `@dispatcher`, круглые числа).
- Папка `private/` в git не попадает (она в `.gitignore`): там настоящие профиль, прайс, список слов-маркеров и собранный настоящий гайд. Не добавляйте её файлы в репозиторий, в том числе через `git add -f`.
- Внутренние документы (`*.docx`, `*.pdf`, `*.jpg`, `*.jpeg`) в репозиторий не добавляются. Снимки экрана — только с демо-данными.
- Добавляйте в коммит файлы явным списком: `git add путь/к/файлу`, а не всё подряд.
- Перед коммитом запускайте `python tools/check_public.py`. Подробнее о том, что где хранится и как работает проверка, — в [docs/privacy.md](docs/privacy.md).

## Коммиты и pull request

- Работайте в отдельной ветке от `main`; одна тема — один pull request.
- Сообщение коммита — одна строка вида `тип: короткое описание`, по-русски. Типы: `feat:` (новая возможность или шаг), `fix:` (исправление), `docs:` (документы), `test:` (тесты), `chore:` (служебное: CI, `.gitignore`, обновление действий). Например: `docs: правила участия и безопасности`.
- Заметные для пользователя изменения запишите в `CHANGELOG.md`, в раздел «Не выпущено» (формат Keep a Changelog).
- В pull request заполните чек-лист из шаблона `.github/PULL_REQUEST_TEMPLATE.md`: что изменено и зачем, проверка прошла, данных компании нет.
- CI (`.github/workflows/ci.yml`) на каждый push и pull request запускает те же проверки на Python 3.12. Чтобы pull request приняли, CI должен быть зелёным.

Вопрос или идея, которые не тянут на pull request, — это issue: выберите форму «Ошибка» или «Предложение». Пустые issue отключены.

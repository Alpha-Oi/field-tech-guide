# Архитектура

Из текстов гайда, профиля компании и прайса команда `python guide/build.py` собирает три файла: страницу `index.html`, текстовую версию `guide.md` и записку техдиру `for-techdir.md`. Тексты и данные компании отделены от кода: движок ничего не знает ни о названиях приложений, ни о ценах. Всё написано на Python 3 и на стандартной библиотеке, страница — на чистых HTML, CSS и JS без сборщика.

Здесь описано, что где лежит. Почему так, а не иначе, объясняют [записи решений](adr/README.md); значения слов проекта — в [словаре CONTEXT.md](../CONTEXT.md).

## Слои

```text
guide/content/*.json         тексты по этапам и памятка на заявку
guide/profiles/*.json  ──►   guide/build.py   ──►   index.html       страница для телефона
  профиль (значения          читает, проверяет,     guide.md         текст для чата и печати
  компании) и прайс          подставляет, рисует    for-techdir.md   записка техдиру
guide/docs/for-techdir.md    шаблон записки
```

1. **Контент.** Тексты лежат в `guide/content/*.json`, один файл на этап, плюс файл памятки на заявку. Файлы читаются по порядку имён. Тексты нейтральные: всё, что принадлежит компании, записано переменной `{{имя}}`. Схема — в [CONTRIBUTING.md](../CONTRIBUTING.md).
2. **Профиль.** Значения переменных: `guide/profiles/demo.json` (публичное демо с вымышленными примерами) или `private/profile.json` (настоящий, вне git). Смысл каждой переменной — в `guide/profiles/VARS.md`. Сборка собирает все `{{имя}}` из контента и записки и требует, чтобы каждая была в профиле; лишняя переменная в профиле — только предупреждение. Флаг `--lenient-vars` превращает неизвестные переменные из ошибки в список.
3. **Прайс.** Отдельный JSON: позиции и таблицы «модель × услуга». По умолчанию берётся `guide/profiles/demo-pricelist.json`, свой подключается флагом `--pricelist`, а `--no-pricelist` собирает без прайса. Переменные профиля в прайс не подставляются: это обычный текст. Схема и правила — в [pricelist.md](pricelist.md).
4. **Сборка.** `guide/build.py` читает всё перечисленное, проверяет, подставляет значения профиля и рисует три файла. Если контент или прайс не проходит проверку, сборка печатает ошибки по-русски с указанием места и завершается с кодом 1, ничего не записав.
5. **Страница, текст, записка.** `index.html` — страница; `guide.md` — тот же гайд текстом; `for-techdir.md` — записка техдиру с подставленными значениями профиля.

## Границы

Проект разделён на семь частей. У каждой есть владелец данных, то, что она отдаёт, и то, что она скрывает от соседей.

| Часть | Владеет | Отдаёт | Скрывает |
|---|---|---|---|
| 1. Контент | текстами гайда | JSON по схеме: этапы, шаги, памятка | вёрстку и порядок вывода на странице |
| 2. Профиль | значениями, которые принадлежат компании | имя профиля и словарь переменных | где и как переменные используются |
| 3. Сборка | чтением, проверкой, подстановкой и рендером | три файла и понятные ошибки | устройство страницы |
| 4. Страница | вёрсткой, стилями и поведением | работающую страницу из данных `guide-data` | всё остальное |
| 5. Записка техдиру | рекомендациями по внедрению гайда | шаблон `guide/docs/for-techdir.md` с переменными профиля | детали гайда |
| 6. Защита от утечки | проверкой публичных файлов | код возврата и список находок | сами слова-маркеры |
| 7. Прайс | данными прайса | JSON, из которого страница строит панель «Прайс и акт» | как панель считает акт |

## Модуль сборки

Модуль `guide/build.py` можно запускать как скрипт и импортировать (`from guide import build`). Его публичные функции:

| Функция | Что делает |
|---|---|
| `load_content` | читает все `*.json` из папки контента по порядку имён: этапы и памятку |
| `load_profile` | читает профиль и проверяет его форму: имя и словарь строковых переменных |
| `load_pricelist` | читает прайс |
| `apply_profile` | возвращает новую структуру с подставленными переменными; рантайм-токены `{{order}}` и `{{phone}}` и ключи отчётов не трогает |
| `validate` | возвращает список понятных ошибок контента (и прайса, если он есть); пустой список — всё в порядке |
| `validate_pricelist` | то же для прайса |
| `coverage` | сверяет шаги со списком требований (флаг `--manifest`) |
| `render_md` | текстовая версия `guide.md` |
| `render_html` | вставляет данные в шаблон страницы вместо маркера `<!--GUIDE_DATA-->` |
| `render_techdir` | подставляет профиль в шаблон записки |

Порядок в командной строке: прочитать контент и найти в нём переменные, прочитать профиль, прайс и шаблон записки, сверить переменные, подставить профиль, проверить контент и прайс (и покрытие требований, если задан `--manifest`). Только если ошибок нет, все три файла сначала рисуются в памяти и лишь потом записываются в папку `--out`, с окончаниями строк LF. Поэтому при ошибке в выходной папке ничего не меняется.

Две разновидности меток `{{…}}`:

- **переменные профиля** (`{{app_name}}` и т. п.) подставляет сборка; они допустимы в любой строке контента;
- **рантайм-токены** `{{order}}` и `{{phone}}` подставляет страница из полей «Памятки на заявку»; они допустимы только в готовых сообщениях для чата. В `guide.md` они выводятся заглушками `[НОМЕР ЗАЯВКИ]` и `[ТВОЙ ТЕЛЕФОН С 8]`.

## Страница

Страница — один файл `guide/template.html`. В нём стили, разметка и скрипт; данные приходят из блока `<script type="application/json" id="guide-data">`, который `render_html` вставляет на место маркера `<!--GUIDE_DATA-->`.

- **Нет внешних подключений.** Нет CDN, внешних шрифтов, аналитики, картинок по ссылкам и внешних скриптов, страница работает без интернета после открытия. Тест проверяет, что в шаблоне нет внешних адресов и сетевых вызовов.
- **Данные не становятся HTML.** Всё, что приходит из данных, попадает в страницу через `textContent` и `createElement`. Разметка `**жирный**` разбирается собственным разбором в узлы `<strong>`. Кликабельны только ссылки `https://`.
- **Логика отдельно от DOM.** Часть скрипта между строками `/* logic:start */` и `/* logic:end */` — обычные функции без обращений к DOM: разбор разметки, подстановка токенов, расчёт отчёта, подсчёт прогресса и готовности, а для прайса поиск, строки выбора и расчёт акта. Python-тест вырезает этот блок и запускает через `node`; без `node` такие тесты пропускаются, а в CI (`REQUIRE_NODE=1`) без него падают. Код панели «Прайс и акт» лежит между `// price:start` и `// price:end`, а её кнопка и сама панель создаются, только если в данных есть ключ `pricelist`.
- **Прогресс.** Отметки хранятся в `localStorage` под ключом `masterGuide.progress.v1`: объект `{"<id шага>": true}`. Идентификаторы, которых нет в данных, игнорируются, поэтому `id` шага после выпуска не меняют. Каждое обращение к `localStorage` и буферу обмена обёрнуто в `try/catch`: если хранилище недоступно, страница работает, не помнит отметки и одной строкой говорит об этом.
- **Личное живёт в памяти.** Номер заявки, телефон и выбор услуг в панели «Прайс и акт» не записываются ни на диск, ни в `localStorage`. Подробнее — в [privacy.md](privacy.md).
- **Для телефона и печати.** Одна колонка, крупный текст, светлая и тёмная тема (по настройке системы), печатный вид через `@media print`.

## Проверка утечек

`tools/check_public.py` защищает публичный репозиторий от данных компании. Он берёт список файлов у git (`git ls-files` вместе с ещё не добавленными, но не игнорируемыми файлами), а если git недоступен — обходит дерево, пропуская `.git`, `dist`, `private` и служебные папки. В этих файлах он ищет:

- запрещённые расширения: `docx`, `pdf`, `jpg`, `jpeg`;
- пути к диску D и к папке пользователей диска C;
- слова-маркеры из `private/markers.txt` или из файла, названного флагом `--markers`: по слову на строку, регистр не важен, пробелы и невидимые символы между словами не мешают. Сами слова в вывод не попадают: печатается номер маркера, а в именах файлов слово заменяется на `***`.

Код возврата 0 — чисто, 1 — есть находки; каждая печатается как `файл:строка — причина`. Предупреждения (двоичный файл с текстовым расширением, пустой список маркеров) код возврата не меняют. В CI файла `private/markers.txt` нет, поэтому там проверяются только расширения и пути. Что именно нельзя класть в публичный репозиторий и как вести список маркеров — в [privacy.md](privacy.md).

## График и снимки

`tools/make_charts.py` читает `guide/content/*.json` (файлы с блоком `stage`; памятка пропускается) и пишет `docs/img/steps-by-stage.svg`: горизонтальный столбчатый график «Шагов по этапам», обязательные и дополнительные шаги разными цветами. Скрипт использует только стандартную библиотеку, а результат один и тот же при каждом запуске. После правки контента график перестраивают командой `python tools/make_charts.py`; `python tools/make_charts.py --check` ничего не пишет и завершается кодом 1, если файл в репозитории устарел или правился руками. Эта проверка входит в команду проверки целиком.

В папке `docs/img/` лежат ещё снимки страницы и картинка для карточки репозитория: они сняты на демо-профиле и демо-прайсе, без данных компании. Что допустимо на снимках — в [privacy.md](privacy.md).

## Тесты и CI

Тесты лежат в `guide/tests/`: `test_build.py` (сборка и проверка контента), `test_pricelist.py` (прайс), `test_page_logic.py` и `test_page_price.py` (логика страницы через `node`), `test_check_public.py` (проверка утечек), `test_repo.py` (демо-профиль, записка, служебные файлы), `test_workflows.py` (workflow), `test_community.py` (документы проекта), `test_node_gate.py` (что без `node` тесты страницы не пропускаются молча в CI). Общий доступ к `node` — в `guide/tests/_node.py`.

Workflow лежат в `.github/workflows/`:

- `.github/workflows/ci.yml` на каждый push и pull request запускает на Python 3.12 проверку целиком (тесты, контент, утечки, актуальность графика), затем строгую проверку демо-профиля и пробную сборку демо;
- `.github/workflows/pages.yml` при push в `main` повторяет проверку, собирает демо и публикует его на GitHub Pages. Права на запись в Pages получает только последняя задача. Публикуется только демо с нейтральным профилем; как раздать настоящий гайд — в [deploy.md](deploy.md).

Версии действий в workflow закреплены, а `.github/dependabot.yml` раз в неделю предлагает их обновить.
